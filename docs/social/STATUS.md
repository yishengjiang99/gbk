### Doc vs prod (checked 2026-10-25 against prod 44b3be2)

- `preview`: prod sends `{ tracks: [color], lo, hi, end, notes: [[trackIndex, start, length, pitch]] }`; the doc says `{ notes: [[pitch, start, dur, track]], duration }`. The iOS model accepts both.
- `GET /api/session` returns `{ authenticated, user, name, provider, csrf, enabled, providers, loginAvailable, reviewerLogin, limits }`, not `{ user, csrf, me }`.
- 404s for unbuilt routes use Fastify's `{ message, error, statusCode }`, not `{ code, message }`.
- `/t/<tag>` is a tag deep link (the M0 app treated it as a thread; fixed).

### Feed visuals vs web (2026-10-25)

Mirrors `src/components/social/LiveRoll.tsx`: PLAYHEAD_X 0.25, WINDOW_SEC 4, BARS 48, BAR_DECAY_MS 150, F_LO 40 / F_HI 16000, bar hue 200→340°, active note `brighten(0.45)` + glow, inactive alpha 0.85, note height 0.85 row, pitch span ≥ 12.
Differences: iOS hides notes once they finish (per the iOS card spec), while web LiveRoll still draws them in the 1 s left of the playhead. iOS also adds the Export video's black-key row stripes. The Export video itself uses an 8 s window with the playhead at 30%; the feed cards use the LiveRoll values. Bars are scaled from dB like the AnalyserNode defaults (-100…-30 dB). The oscilloscope is iOS only for now.

### iOS native Hum: bridge contract for GBK Social (web)
- iOS injects `window.gbkNative = { platform: "ios", version: 1, capabilities: ["hum"] }` before page scripts run.
- When `gbkNative?.capabilities?.includes("hum")`, render the mic button in the always-visible composer prompt bar (instead of the web Hum flow), and on tap call `webkit.messageHandlers.hum.postMessage({ type: "toggle" })`. The first tap starts, the second stops.
- Expose `window.gbkHum`:
  - `context()` → `{ ppq, tempos: [{ tick, microPerQuarter }], tracks: [{ channel }], readOnlyReason: string | null }` (from `workstation.project` / `workstation.readOnlyReason`).
  - `apply(ops, { label, selectTrackId })` → `workstation.userEdit(ops, { label })` (one undo step), then `setSelection({ trackIds: [selectTrackId], noteIds: [] })`. Return `{ ok: true }` or `{ ok: false, error }`. The ops are exactly `humToOps` output (`addTrack` "Hummed melody", program 0, role melody, plus `addNotes`).
  - `showReadOnlyHint(reason)` → `readOnlyHintListeners`.
  - `onState({ phase: "idle" | "recording" | "transcribing", elapsed, progress })` → button label (`⏺ m:ss Stop` / `🎤 NN%` / `🎤 Hum`).
- Reference implementation of the web side: `ios/GBKComposer/Resources/HumTest/hum-harness.html`.
- **Web side live** (`src/hum/native-bridge.ts`, spec `docs/social/hum-bridge.md`): `apply` validates humToOps-shaped ops and adds a new "Hummed melody" track; returns `{ ok, trackId, notes, revision }`.
